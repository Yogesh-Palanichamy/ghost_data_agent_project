# Evaluation Report — Ghost Data Still Exists

## Evaluation scope

The 518-row `output.csv` was generated by running `python code/main.py` against `dataset/deletion_requests.csv`, the supplied identity/audit/activity CSVs, `deletion_rules.csv`, `evidence_files.csv`, and the local evidence corpus. The output validator passed the header, row count, ordering, JSON schema, step numbering, phase/operation ordering, evidence-reference, and status-specific evidence checks.

The organizer supplied reference answers for the 32 public sample requests. Those are used only by `evaluation/main.py` for measurement; the prediction pipeline does not load `sample_output.csv` when generating `output.csv`.

## Public-sample metrics

| Metric | Result | Definition |
|---|---:|---|
| Case-level status accuracy | 31/32 = **96.9%** | Exact match on `deletion_status` for each public sample case |
| Exact `steps_json` match | 12/32 = **37.5%** | Entire ordered step array matches the reference |
| Step-object accuracy | 126/207 = **60.9%** | Exact step-object matches at aligned positions divided by the maximum aligned positions across cases |
| Field-level accuracy | 1,093/1,449 = **75.4%** | Exact matches for `step_no`, `phase`, `system_id`, `resource_id`, `operation`, `state`, and `evidence_id` at aligned positions |
| Sequence accuracy | 16/32 = **50.0%** | For equal-length arrays, every aligned `phase` and `operation` matches |

These are public-sample results, not a claim about hidden-case accuracy. No canonical answers are available for the 518 prediction cases, so full-dataset accuracy cannot be measured locally.

## Additional evaluation cases created by the team

1. **Correction without deletion** — changing a phone number while keeping the account active must return `NOT_APPLICABLE` intent.
2. **Explicit not-to-erase request** — an information-access request that explicitly says it is not a request to erase must not authorize deletion.
3. **Portuguese deletion request** — recognize `exclusão permanente` as deletion intent.
4. **Korean deletion request** — recognize `삭제` as deletion intent.
5. **Retained tombstone** — a tombstone retaining a stable `user_id` but no direct identifiers is compliant with the redaction rule.
6. **Analytics email hash** — an analytics profile that retains an email hash must be treated as attributable and require anonymization.

The executable tests are in `evaluation/custom_cases.py`.

## Failures found and improvements made

- **Cross-line log correlation:** initial parsing missed identifiers recorded on a trace-start line and the resource ID recorded on a completion line. The parser now groups log lines by `trace_id` before matching identities.
- **Local evidence formats:** added SQLite-backed SQL parsing, nested JSON parsing, log parsing, text handover parsing, PDF text extraction, and screenshot OCR when `pdftotext`/`tesseract` are available.
- **Historical identifiers:** current identity fields and historical audit values are resolved into a per-request identifier set; phone formatting and email hashes are handled separately.
- **Policy handling:** policy categories/actions are loaded from `deletion_rules.csv`; backup restore risk and active data-flow risk are treated as operational conditions.
- **Null normalization:** literal strings such as `"null"` no longer count as retained identifiers. Correlation hashes remain identifying values.
- **Operational risk fallback:** when state snapshots are missing, explicit failed/partial deletion/redaction/anonymization events and explicit “remains enabled” / “can still be restored” checks produce conservative remediation plans. Activity success results are not used as proof that a record is absent.
- **Intent handling:** added negative-request detection and Portuguese/Korean deletion terms to reduce false deletion authorization.

## Remaining limitations

- One public sample status remains incorrect: `case_04` is conservatively marked `INCOMPLETE` because the available evidence does not provide a defensible direct link from `user_04` to the absent `account_004` resource. The implementation intentionally avoids hardcoding a case-to-resource mapping. A later conservative correlation change reduced unsupported event-only matches but did not resolve this ambiguity.
- Exact step arrays remain less accurate than status labels. The largest remaining sources are resource-to-subject ambiguity where snapshots omit identifiers, activity timelines containing several resources close together, and differences in which supporting verification records the reference output includes.
- Some cases have no direct pre-audit record snapshot. The system uses explicit catalog links and unresolved activity risks where possible, but those inferred relationships should be reviewed before treating the output as a legal deletion certificate.
- OCR quality depends on local `pdftotext` and `tesseract` availability and the legibility of supplied media.

## Iteration performed for this package

- Prevented the operational-risk fallback from attaching a nearby event to a user unless its resource is already linked by evidence or the event details contain a resolved identifier. This reduces false-positive cross-user matches, but can leave a case unresolved when the evidence corpus lacks an explicit identity link.
- Added reported workflow result as a secondary tie-breaker when multiple account-deletion events occur in the same reporting window. It remains a locator heuristic, never proof of deletion state.
- Re-ran the complete public sample evaluation and all six authored synthetic tests after these changes. Sample status accuracy remained 31/32; exact step-array match improved from 11/32 to 12/32.

## Recommended next improvements

1. Build an explicit resource-identity graph using all `LINK_RESOURCE_IDENTITY` events, source-resource references, and per-system resource aliases.
2. Add dependency-aware temporal reconstruction for sync/import/restore events, with separate handling for event claims versus state snapshots.
3. Improve policy-specific field extraction for support records, tombstones, analytics hashes, and regional SQL replicas.
4. Add targeted regression tests for every public sample mismatch and compare alternative resource-linking heuristics before final submission.
